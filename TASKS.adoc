= TCK Integration Tasks
:toc: left
:icons: font

== 1. Overview

This document breaks down the work required to complete the TCK integration into a set of actionable, hierarchical tasks. These tasks are derived from the goals in `TCK-REQUIREMENTS.adoc` and the technical plan in `TCK-SPEC.adoc`.

Each high-level task is suitable for a feature branch and pull request. Sub-tasks represent individual, committable units of work.

== 2. Task Breakdown

=== TASK-1: Set up TCK Test Environment

*Description*: Establish the necessary local environment to run the TCK test harness against a placeholder implementation. This ensures the runner and our code can communicate before any logic is implemented.
*Parent Task*: None
*Dependencies*: None

==== TASK-1.1: Create `bin` Directory
*Description*: Create a `bin/` directory in the project root to house the TCK adapter script and other executable helpers.
*Constraints*:
- The directory must be named `bin` and be at the root of the project.
*Acceptance Criteria*:
- A `bin/` directory exists in the project root.
- The directory is added to Git.

==== TASK-1.2: Add TCK as a Project Dependency
*Description*: Add the official AsciiDoc TCK repository as a Git submodule in a `vendor/` directory. This allows us to version-lock the TCK and easily update it.
*Constraints*:
- The TCK repository must be added as a Git submodule, not just cloned.
- The submodule must be placed in a `vendor/asciidoc-tck` directory.
*Implementation Note*:
The following command should be used:
[source,bash]
----
git submodule add https://gitlab.eclipse.org/eclipse/asciidoc-lang/asciidoc-tck.git vendor/asciidoc-tck
----
*Acceptance Criteria*:
- A `.gitmodules` file is created or updated.
- The `vendor/asciidoc-tck` directory contains the TCK source code.

==== TASK-1.3: Create Placeholder TCK Adapter
*Description*: Create an empty executable script at `bin/tck-adapter.py`. Initially, it can simply exit with a status code of 0.
*Constraints*:
- The script must be executable (`chmod +x`).
- It must have a shebang line (e.g., `#!/usr/bin/env python`).
*Acceptance Criteria*:
- The file `bin/tck-adapter.py` exists and is executable.
- Running the script exits with a status code of `0`.

==== TASK-1.4: Create TCK Runner Script
*Description*: Create a shell script (`run-tck.sh`) that invokes the Node.js-based TCK runner, pointing it at our placeholder adapter. This validates the basic setup.
*Constraints*:
- The script must be executable.
- Requires `node` (>= 20) and `npm` to be installed on the system.
*Implementation Note*:
The TCK's dependencies must be installed first by running `npm ci` inside the `vendor/asciidoc-tck` directory.
*Acceptance Criteria*:
- A `run-tck.sh` script exists in the project root.
- Running the script executes the TCK harness, which in turn invokes our placeholder adapter.
- The script should not fail, even though no tests will pass.

=== TASK-2: Implement TCK Adapter

*Description*: Implement the command-line script that will serve as the bridge between the TCK runner and the parser.
*Parent Task*: None
*Dependencies*: TASK-1

==== TASK-2.1: Implement `stdin` Parsing
*Description*: Add logic to `bin/tck-adapter.py` to read from `stdin` and parse the incoming JSON payload from the TCK runner.
*Ref*: `TCK-SPEC.adoc`, Section 3.2
*Constraints*:
- Must use the standard `sys` and `json` libraries.
- Must correctly handle the JSON structure defined in the TCK specification.
*Acceptance Criteria*:
- The script can successfully parse a valid JSON input from `stdin`.
- The `contents` field of the JSON payload is extracted into a variable.

==== TASK-2.2: Invoke the Parser
*Description*: In the adapter, call the main `parse_to_ast` function with the AsciiDoc source from the parsed `stdin` payload.
*Constraints*:
- Must import the `parse_to_ast` function from the `asciidoc_parser` library.
*Acceptance Criteria*:
- The `parse_to_ast` function is called with the AsciiDoc source.
- The returned AST is stored in a variable.

==== TASK-2.3: Implement Basic Error Handling
*Description*: Wrap the parser invocation in a `try...except` block. On any exception, print the error to `stderr` and exit with a non-zero status code.
*Ref*: `TCK-SPEC.adoc`, Section 3.4
*Constraints*:
- Must catch all exceptions from the parser.
*Acceptance Criteria*:
- If the parser raises an exception, a message is written to `stderr`.
- If the parser raises an exception, the script exits with a non-zero status code.

==== TASK-2.4: Implement `stdout` Writing
*Description*: Add logic to serialize a dictionary to a JSON string and print it to `stdout`. Initially, this can be a hardcoded "Hello, World" dictionary.
*Ref*: `TCK-SPEC.adoc`, Section 3.3
*Constraints*:
- The output must be a valid JSON string.
*Acceptance Criteria*:
- The script prints a JSON object to `stdout` on successful execution.
- The script exits with a status code of `0`.

=== TASK-3: Implement AST to ASG Transformer

*Description*: Create the logic to transform the parser's internal AST into the TCK-compliant ASG.
*Parent Task*: None
*Dependencies*: TASK-2

==== TASK-3.1: Analyze TCK's ASG JSON Schema
*Description*: Locate the ASG JSON schema within the TCK repository, analyze its structure, and document the findings. This is a critical prerequisite for a compliant transformation.
*Constraints*:
- The schema is likely a `.json` file within the `vendor/asciidoc-tck` directory.
*Acceptance Criteria*:
- The path to the ASG JSON schema file is identified.
- A summary of the schema's top-level structure and key node types is added to the `ARCHITECTURE.adoc` file for future reference.

==== TASK-3.2: Create `ASGVisitor` Class
*Description*: Create a new file `src/asciidoc_parser/asg_visitor.py` and define an `ASGVisitor` class that inherits from `NodeVisitor`.
*Ref*: `TCK-SPEC.adoc`, Section 4.1
*Dependencies*: TASK-3.1
*Constraints*:
- The new file must be correctly placed within the `src/asciidoc_parser` module.
*Acceptance Criteria*:
- The file `src/asciidoc_parser/asg_visitor.py` exists.
- It contains a class `ASGVisitor` that inherits from `NodeVisitor`.

==== TASK-3.3: Implement Visitor for Simple Nodes
*Description*: Implement `visit` methods in `ASGVisitor` for a small subset of core nodes (e.g., `Document`, `Paragraph`, `Text`) to produce a dictionary structure.
*Constraints*:
- The output dictionary structure must conform to the ASG schema identified in TASK-3.1.
*Acceptance Criteria*:
- The `ASGVisitor` has methods like `visit_document`, `visit_paragraph`, and `visit_text`.
- Visiting a simple AST returns a nested dictionary that is valid against the ASG schema.

==== TASK-3.4: Integrate Visitor into Adapter
*Description*: Update `bin/tck-adapter.py` to instantiate `ASGVisitor` and use it to traverse the AST returned by the parser.
*Constraints*:
- Must correctly import the `ASGVisitor`.
*Acceptance Criteria*:
- The adapter script creates an instance of `ASGVisitor`.
- The visitor's `visit` method is called with the root of the AST.

==== TASK-3.5: Serialize ASG to `stdout`
*Description*: Replace the hardcoded dictionary from TASK-2.4 with the dictionary produced by the `ASGVisitor`.
*Constraints*:
- The output must be valid JSON.
*Acceptance Criteria*:
- The adapter now outputs a JSON representation of the transformed AST.

==== TASK-3.6: Implement Visitor for All Nodes
*Description*: Incrementally add `visit` methods for all remaining nodes defined in `nodes.py`. This is an ongoing task that will be parallel to fixing TCK failures.
*Constraints*:
- Each new visitor method must produce output that conforms to the TCK's JSON schema for that node type.
*Acceptance Criteria*:
- The `ASGVisitor` class has a `visit` method for every node type in `nodes.py`.
- The output for each node type is compliant with the TCK's expectations.

=== TASK-4: Integrate TCK into Project Test Suite

*Description*: Automate the execution of the TCK harness within the project's `pytest` suite.
*Parent Task*: None
*Dependencies*: TASK-1, TASK-2, TASK-3

==== TASK-4.1: Create `pytest` TCK Test File
*Description*: Create a new test file, `tests/test_tck.py`.
*Constraints*:
- The filename must follow `pytest` conventions.
*Acceptance Criteria*:
- The file `tests/test_tck.py` exists.

==== TASK-4.2: Create TCK Runner Fixture
*Description*: In `tests/test_tck.py`, create a `pytest` fixture that uses the `subprocess` module to execute the `run-tck.sh` script and capture its output.
*Constraints*:
- The fixture must be reusable by multiple test functions.
*Acceptance Criteria*:
- A `pytest` fixture is defined that runs the TCK harness.
- The fixture returns the `stdout` and `stderr` of the TCK runner.

==== TASK-4.3: Add Initial TCK Test
*Description*: Write a test function that uses the fixture to run the TCK. The test should parse the runner's output and assert that the number of failing tests is below a certain threshold.
*Constraints*:
- The test must parse the TCK runner's output to find the number of failures.
*Acceptance Criteria*:
- A test exists that fails if the number of TCK failures increases unexpectedly.

==== TASK-4.4: Implement `xfail` for Known Failures
*Description*: Create a mechanism to mark known TCK failures as `pytest.xfail`. This allows the test suite to pass while we work towards full compliance. The list of known failures should be easy to update.
*Constraints*:
- The list of known failing tests should be stored in a separate, easily editable file (e.g., a `.txt` file).
*Acceptance Criteria*:
- The `pytest` test suite passes, with known TCK failures marked as `xfail`.
- Removing a test name from the known failures list causes the corresponding `pytest` test to fail.

=== TASK-5: Iteratively Achieve Full TCK Compliance

*Description*: The ongoing process of using the TCK harness to find and fix compliance issues.
*Parent Task*: None
*Dependencies*: TASK-4

==== TASK-5.1: Establish TCK Failure Analysis Process
*Description*: Document the process for analyzing a TCK failure reported by the `pytest` suite, from identifying the root cause to creating a bug-fix branch.
*Ref*: `TCK-REQUIREMENTS.adoc`, REQ-06
*Constraints*:
- The process should be documented in `CONTRIBUTING.adoc`.
*Acceptance Criteria*:
- A new section in `CONTRIBUTING.adoc` explains how to work on TCK failures.

==== TASK-5.2: Create GitHub Issues for Failures
*Description*: For each unique TCK failure, create a new GitHub Issue. The issue should include the input AsciiDoc, the expected ASG, the actual ASG, and a link to the relevant part of the AsciiDoc specification.
*Constraints*:
- Issues should be tagged with a `tck-failure` label.
*Implementation Note*:
Use the following template for the issue body:
[source,markdown]
----
### TCK Failure Report

**Test Case:** `[Name of the failing test case]`

**Specification Reference:** `[Link to the relevant section of the AsciiDoc spec, if known]`

---

**Input AsciiDoc:**
```asciidoc
[Input that caused the failure]
```

---

**Expected ASG (Diff):**
```diff
- [Relevant part of the expected ASG]
+ [Relevant part of the expected ASG]
```

---

**Actual ASG (Diff):**
```diff
- [Relevant part of the actual ASG]
+ [Relevant part of the actual ASG]
```

---

**Analysis:**
[Brief analysis of the root cause, if known. e.g., "The parser is incorrectly creating a `Strong` node instead of an `Emphasis` node."]
----
*Acceptance Criteria*:
- A clear, consistent format for TCK failure issues is adopted.

==== TASK-5.3: Prioritize and Fix Failures
*Description*: Triage the created issues and address them according to project priorities. This will involve fixing bugs in the grammar (`grammar.lark`), the CST-to-AST transformer (`lark_parser.py`), or the AST-to-ASG visitor (`asg_visitor.py`).
*Constraints*:
- Each fix must be developed on a separate branch.
- Each fix must include a `pytest` test that fails before the fix and passes after.
*Acceptance Criteria*:
- A TCK test that was previously failing is now passing.
- The corresponding GitHub Issue is closed.

==== TASK-5.4: Update `xfail` List
*Description*: As bugs are fixed and TCK tests pass, remove them from the list of known failures in `tests/test_tck.py`. The goal is to eventually make this list empty.
*Constraints*:
- The `xfail` list must be updated in the same commit that fixes the underlying bug.
*Acceptance Criteria*:
- The number of `xfail`ed tests in the `pytest` suite decreases.
